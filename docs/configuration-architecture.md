右ペインは概要・状態・保有情報に分けた。中央設定画面はカテゴリ・検索・折りたたみを備え、登録された標準項目からフォームを描画する。資源、基本属性、群配置、移動ばらつき、探知・通信、周期報告、命令許可元、初期情報、リンク・障害、停止復旧事象、モデル前提を編集できる。ノード・経路の専用エディタも中央画面へ載せ、保存は同じ下書きへ戻す。専用編集を閉じた後、共通画面の適用で一つのUndoとして確定する。

未対応の資源分析Bindingは理由を表示する。探知装置の伝搬遅延・継続障害など、既存ファイルに受け入れられるが現探知計算で使用しない属性は編集不可の理由を表示して保持する。新しい物理作用を実装したと誤認させない。

## 検査と適用範囲

`npm run check:configuration` は実際の入力・モジュール編集部品を読み、未登録の部品、設定ID重複、所有者・未設定の意味、単位倍率、編集不可理由、分析への接続、状態契約と生成仕様表を確認する。標準数値を契約へ追加すれば、手書きHTMLを追加せず入力が生成される。仕様変更時は `node tools/check-configuration.mjs --write` で仕様表を更新する。

検査対象は登録された公開設定である。任意の計算コードに隠れた属性を静的解析して完全に発見する仕組みではない。新しい公開設定は契約登録を必須とし、専用部品は入口・編集・保存をブラウザ検証する。従来のノード構造・挙動担当値・地形・分析アルゴリズム設定の全体を一般フォームへ移したわけではなく、既存の専用エディタと検証を使う。未知の拡張キーを一括拒否する移行は行わず、編集時に保持する。資源IDごとの比較変数、装置複数搭載、受信していない味方資源の表示などは未対応。

以下は設計時の方針と段階順を残したもの。現状説明は画面版27時点の履歴である。

## 起きた問題と現状

資源の計算とファイル検証が実装されていても、容量・消費率を割り当てる画面がなかった。画面版27で入口を追加したが、同じ種類の欠落を防ぐ構造はまだない。

現行では次が別々の場所にある。

| 役割 | 現在の実装 | 問題 |
| --- | --- | --- |
| 資源の入力検証・状態更新 | `src/resources.js` | 編集入口の存在を要求しない |
| 資源フォームの型・範囲・単位変換 | `src/resource-ui.js` | 検証側と独立に定義している |
| 分析変数の名前・範囲・単位・対象 | `src/parameters.js` | 分析用の数値台帳で、全設定の台帳ではない。資源の数値は未登録 |
| 右ペインの配置・表示・変更 | `index.html`, `src/app.js` | 項目追加のたびにHTML・表示処理・変更処理を個別に追加する |
| 初期情報・命令の許可元等 | `src/information-settings.js` | ファイル検証はあるが、専用の入力画面がない |
| 通信リンク・継続障害・並行報告 | `src/communication.js` | ファイルで設定できる項目と通常画面で編集できる項目が一致しない |

一方、定義を複製して検証し、適用後にUndoへ積む`app.js`の`commit()`、単体・群・共有担当の編集元を解決する`editor.js`、専用ノード／経路エディタは利用する。全体を新しいデータ形式へ一度に置き換えない。

## 開発上の契約

**公開する設定には、型・保存先・編集方法・適用範囲を必ず登録する。登録された編集可能な設定に入口がなければビルドを失敗させる。**

「計算できるから機能完成」という扱いを廃止する。新機能の完成条件は、入力の契約、計算による使用、編集入口、保存／読込、対象範囲、状態の参照権限がそろうこと。分析対象・盤面表示は機能ごとに要否を宣言し、すべての数値を分析変数や地図ラベルにしない。

設定契約はドメインごとの純粋なJavaScript定義とする。DOM・Three.js・Worker・外部通信に依存しない。標準フィールドはこの定義から検証・フォーム・仕様表を作る。グラフ、地図、関係の一覧などは専用エディタを登録する。

JSON Schemaを導入するかは別の実装判断とする。型のスキーマだけでは、どこで編集するか、群の何を変えるか、誰に状態が見えるかまでは規定できない。今回必要なのはそれらを含むアプリケーションの契約である。

## 一つに定義する内容

| 宣言 | 内容 |
| --- | --- |
| 識別 | 安定した設定ID、日本語名、説明、対応シナリオ版 |
| 型・制約 | 数値・選択肢・参照・配列・繰り返しコレクション、必須、上下限、関連制約 |
| 値の意味 | 固定性能／初期状態／モデル前提。計算中の状態や派生値は別契約 |
| 単位 | 保存単位、表示単位、往復変換。資源の量を勝手にkgやLと解釈しない |
| 未設定の意味 | 制約なし、未搭載、既定値、情報不明を区別。明示しない値を保存時に一律に埋めない |
| 所有者・適用範囲 | シナリオ、単体定義、群ひな型、群配置、タスク、ノード、関係のどれか |
| 編集方法 | 標準入力部品、コレクション編集、専用エディタ、編集不可とその理由 |
| 分析への露出 | 比較・状況分布・味方運用の許可／非対応と理由。既存の制約を維持 |
| 参照 | 選択できるIDの型、削除・複製時の参照整理 |
| 再計算 | 定義変更でどの結果が古くなるか。表示設定は計算を無効にしない |

IDは翻訳名やDOMのIDに依存させない。`resource.capacity`のような定義IDと、実際の資源ID・対象IDを組み合わせて設定を解決する。`resources`のような動的なキーの集合、群ひな型、担当値で束縛された値も契約に含める。

資源では「容量」「初期残量」は入力契約、「現在残量」「消費量」「残量割合」は状態契約とする。現在残量を定義フォームに混ぜたり、終了時の残量で初期値を上書きしたりしない。

### 資源設定の宣言例

以下は設計時の宣言例。実装の正本は `src/resource-schema.js` の `RESOURCE_CONTRACT` と `RESOURCE_FIELDS` であり、構文はこの例と異なる。

```js
{
  id: 'unit.resources',
  owner: 'entityDefinition', // 単体、または群のtemplateを編集元として解決
  sinceScenarioVersion: 4,
  schema: {
    kind: 'keyedCollection',
    path: 'resources',
    key: { pattern: '^[A-Za-z0-9_-]{1,64}$' },
    maxItems: 8,
    absentMeaning: 'unconstrained',
    fields: {
      capacity: { id: 'resource.capacity', type: 'number', min: 0.000001, max: 1e12 },
      initial: {
        id: 'resource.initial', type: 'number', min: 0,
        max: { sibling: 'capacity' }, absentValue: { sibling: 'capacity' }
      },
      perMetre: {
        id: 'resource.perMetre', type: 'number', min: 0, max: 1e9,
        absentValue: 0,
        storageUnit: 'quantity/m', displayUnit: 'quantity/km',
        displayMultiplier: 1000
      }
      // 秒／送信当たりの消費、動作別消費、枯渇の影響、補給も同じ契約に登録
    }
  },
  editor: { category: 'capabilities', component: 'resourceCollection' },
  analysis: { supported: false, reason: '資源IDを含む分析Bindingは未実装' }
}
```

各宣言には説明・既定値の意味・入力部品の情報も追加する。動作別消費や補給をコメントのまま実装することは許さず、完全な定義を検査対象にする。

容量と初期値の関係、目的地の存在などは関連検証とする。ラベル・単位変換・単項目の上下限を手書きのフォームへ複製しない。標準部品で扱える数値・選択・参照は共通描画し、資源の追加／削除や並べ方だけを専用部品へ委ねる。

## 分離する層

| 層 | 責務 | 主な接続先 |
| --- | --- | --- |
| 設定契約 | 入力の型・意味・単位・編集範囲 | 検証、標準フォーム、分析台帳、LLM用仕様表 |
| 編集コマンド | 対象解決、差分適用、関連検証、Undo/Redo、結果の無効化 | 地図操作、フォーム、ノード、ファイル読込 |
| 計算モデル | 既存の移動・通信・資源等を計算。入力契約を使用 | Worker、実験、記録 |
| 状態契約 | 状態の型・時刻・観測元・公開範囲・記録可否 | 判断、再生、表示 |
| 表示・編集部品 | 標準入力と専用エディタ、概要カードと状態表示 | 編集画面、右ペイン、盤面 |

中央のレジストリはドメイン定義を集める。資源、探知、通信、情報、運用を一つの巨大なファイルへ押し込まない。WorkerがUI部品を読み込む構造にもしない。既存の`PARAMETERS`は全設定台帳に置き換えるのではなく、分析への露出を許可した設定のビューと、意味のある変更操作を担うアダプタへ移す。

単に保存先へ数値を代入してよいとは限らない。経路位置を変えた時の全経由点の平行移動、共有担当値、群ひな型などは既存の意味を保持する編集コマンドで扱う。

### 共通の編集セッション

1. 選択IDから編集対象を解決する。選択された生成個体と、保存する群ひな型を混同しない。
2. 編集元の定義とrevisionを保持し、下書きへ編集する。
3. 画面に「単体へ適用」「群全8機へ適用」「同じ挙動の担当全員へ適用」等を表示する。
4. 標準フィールドと専用部品が同じ下書きを変更し、項目エラーをその項目へ表示する。
5. 適用時に最新revisionを確認し、関連制約・参照を含めて検証する。編集中に元定義が変わっていたら上書きしない。
6. 一つのコマンドとして適用し、Undo/Redo・再計算待ちへ反映する。取消は保存元を変えない。

能力欄から分析へ移る場合は、設定IDと対象IDを引き継ぎ、同じ数値台帳で解決する。非対応なら理由を出し、実装されていない変数を探索へ渡さない。下書きのある対象を切り替える時は適用／破棄／編集を続けるを表示し、黙って適用や破棄をしない。

### 状態と情報の契約

状態の参照は解析用真状態・本人の状態・受信済み報告を区別する。同じ型を使っても、アクセス先は同一ではない。情報視点と判断へ真状態を渡さず、受信していない味方残量を表示しない。新しい残量や損害指標を追加する時もこの規則を通す。

状態契約は判断可能なフィールド、記録方法、表示単位、集約方法、許可する参照元を宣言する。集約はsum／count／重心／非対応等を明示する。資源IDが同じでも量の単位や意味が異なる定義を無条件に足し合わせない。現形式では資源IDごとに共通単位を使うことを前提とし、混在を扱う新仕様は別のモデル変更として設計する。

表示用の値はその再生時刻のSnapshotから取得し、設定の概要はScenarioDefinitionから取得する。計算状態を定義へ保存しない。状態を直接編集する操作は別途明示的なシナリオ事象にする。

## 右ペインの役割を変える

右ペインは入力フォームを縦に増やす場所ではなく、**選択対象を理解して必要な編集へ移るインスペクタ**とする。上部に対象名・陣営・単体／群の所属を固定し、「概要」「状態」「保有情報」の3つを切り替える。選択状態を明示し、再生時刻と設定値を混ぜない。

| 右ペイン | 表示するもの | 編集の入口 |
| --- | --- | --- |
| 概要 | 担当任務、経路、主な能力、資源設定の要約。未搭載・無制約・未設定を区別 | 主操作は「設定を編集」。要約項目から該当カテゴリへ直接移動可能 |
| 状態 | 現在のノード、位置、速度、稼働、残量、警告。時刻を表示 | 通常は読取専用。関連する設定や履歴へ移動 |
| 保有情報 | 接触・味方報告・命令、観測／受信時刻、鮮度 | 情報視点や関連する判断ノードへ移動 |

折りたたみ欄の追加だけでは、探す場所の問題が残る。カテゴリ内の詳細編集は右ペインから外す。地図でのドラッグや右クリックなど、直接操作できる入口は残し、共通コマンドへ接続する。

### 共通設定画面

「設定を編集」で中央の作業領域を編集モードに切り替える。地図へ戻る操作を固定位置に置き、左の対象一覧は残す。画面内のカテゴリ選択と検索を使い、ダイアログを重ねない。現在のノード・経路エディタはこの編集領域の専用ページとして使う。地図指定時は編集内容を保持して地図へ切り替え、終了後に編集へ戻る。

ユニット編集のカテゴリは次の4つを基本とする。

| カテゴリ | 含める設定 | 今後の追加先 |
| --- | --- | --- |
| 基本・配置 | 名称、陣営、領域、初期位置。群では個数・配置・ひな型 | 編成、機種設定 |
| 能力・資源 | 移動性能、探知装置、通信装置、容量、消費率 | 指向性、搭載装置、攻撃能力 |
| 運用 | 担当タスク、使用経路、周期報告、協調、ノードへの移動 | 交代計画、高度プロファイル |
| 情報・権限 | 初期に持つ情報、命令の許可元 | 報告の共有範囲、命令の許可規則 |

能力と運用を分ける。通信可能な性能と誰へ何秒おきに報告するかは別の設定である。装置や資源は複数件のカード／一覧として同じカテゴリ内へ追加し、新機能ごとに上位タブや右ペインのボタンを増やさない。カテゴリが空でも、その機能を追加できる場合は「未搭載」と追加操作を表示する。対象に適用できないカテゴリは理由を示す。

通信リンク・障害・稼働停止事象はシナリオ／関係の設定、経路は経路の設定、挙動は挙動の設定、実験は分析画面を所有者とする。ユニットの画面には関連設定へのリンクを出す。全シナリオの設定を単体フォームに押し込まない。

検索結果は「設定名・現在値・所有者・カテゴリ」を表示し、該当項目を開いて強調する。検索は入口の補助であり、機能追加時に適切なカテゴリと編集元を登録する責任を代替しない。

## 欠落を止める検査

| 検査 | 失敗させる条件 |
| --- | --- |
| 契約の整合 | 設定ID重複、存在しない所有者・部品・参照型、単位変換未定義 |
| 編集の網羅 | 新しい公開入力が未登録、編集可能なのに標準入力も専用編集の対応宣言もない |
| 専用編集の網羅 | 専用部品の対応フィールドIDが契約の編集対象集合を満たさない |
| 値の往復 | 表示単位で編集→保存→再読込で同じ保存単位の値へ戻らない |
| 適用範囲 | 群編集が生成個体のコピーだけを変更する、共有定義の変更対象が誤る |
| 状態の公開範囲 | 未受信情報や真状態が情報視点・判断へ混入する |
| 機能単位の検証 | 実際の設定入口から編集・保存・読込できない、計算で値が使われない |
| 仕様の同期 | 自動生成した仕様表が契約と一致しない |

台帳を検査するだけでは、既存の手書き検証にこっそり項目を追加した漏れは検出できない。移行済みドメインの公開入力は契約から検証し、契約にない入力を新たに受け付けないことを規約にする。既存ファイルの未移行項目は互換境界で保持し、移行対象として明示する。すべての未知項目を一度に拒否して旧ファイルを壊す移行はしない。

専用エディタの「対応している」という宣言だけでも十分ではない。標準入力は契約から描画し、専用エディタは実際の入口から代表的な編集・保存をするブラウザ検証を併用する。契約は物理モデルの妥当性を証明しない。状態更新や情報伝達の意味はドメインごとの計算テストで確認する。

現在残るファイル専用の設定は「既存・未移行」として名前・入口の状況・移行先を一覧化する。新しく追加するユーザー設定を無期限のファイル専用例外にしない。内部識別子・記録バッファ・派生状態には編集不可を明示し、入力画面を要求しない。

## 段階的な移行（画面版28で実施）

| 順序 | 作業 | 完了の判定 |
| --- | --- | --- |
| 1 | 資源の完全な入力契約、対象解決、検証とフォームの共通化、編集の網羅検査 | 容量等を契約へ追加すると入力が出る。専用編集で未対応なら検査が落ちる。群・保存・Undoの現挙動を保持 |
| 2 | 共通編集画面と右ペインの概要／状態／保有情報を導入。資源を移す | 右ペインへ新しい入力欄を追加せず、概要から資源カテゴリへ到達できる |
| 3 | 移動・探知・通信・配置を契約へ移し、`app.js`の個別入力処理を整理 | 検証範囲・表示単位・編集対象の二重定義をなくす。既存シナリオを意味を変えず保存／読込できる |
| 4 | 初期情報、命令許可元、周期報告、通信リンク・障害・停止事象へ編集入口を付ける | 既存のファイル専用設定を所有者に合った画面で編集できる |
| 5 | 分析台帳・判断フィールド・仕様表の共通参照、専用ノード／経路編集の統合 | 設定から分析へ値と対象を引き継ぎ、対応していない設定を明示。単一ファイルのLLMマニュアルを維持 |

先に右ペインの見た目だけを作り替えない。資源を一つの縦断例として契約→検証→編集→保存まで通し、その仕組みを共通編集画面へ載せてから他のドメインへ広げる。既存の検証・記録・分析・ポータブル版を移行の各段階で確認する。

ファイル形式と計算の意味を維持する限り、UI変更だけで`MODEL_BUILD`を進めない。新しい単位指定、装置を複数搭載する計算モデル等を本当に追加する場合は、入力・モデル・移行規則を別途版管理する。今回の設計案自体はファイル形式や計算結果を変更しない。
