# 条件付き行動と通信（0.5.0）

「何ができるか」は既存の属性・共通パラメータで表現し、「いつ何をするか」はイベントを受けるルールとして分離する。計算は静的配信されたJavaScriptのWorker内で完結し、外部へ情報を送信しない。`src/actions.js`がイベント時刻と出発時刻を決定し、`Simulation.evaluate(time)`が同じ生成経路を任意時刻で評価する。

## 編集とサンプル

地図の「行動・通信」、または選択ユニットの「行動・通信を編集」を開く。対象は単体または群のひな型。生成個体を選んで開くと、その群を編集する。下の例のように条件と動作をリストから選ぶ。適用・Undo/Redo・`.jsn`保存が可能。

「探知・分析」→「探知・対応サンプル」は、UUVの探知 → 管制ノードへの報告 → 対応UAVへの指令 → 準備 → 出発 → 経路終点への到着を例示する。架空の地形・性能・媒体間の通信接続である。到着は捕捉・追尾・攻撃成功ではない。既存の島間通過サンプルも引き続き選べる。

## シナリオの追加フィールド

シナリオ自体の`version`は1のまま。既存の移動・探知設定が正本で、追加フィールドを省略した既存シナリオは従来の探知計算を使う。

```json
{
  "communication": {
    "enabled": true,
    "range": 12000,
    "delay": 30,
    "probability": 0.8,
    "terrainLOS": false
  },
  "behavior": {
    "hold": false,
    "preparation": 0,
    "rules": [
      {
        "id": "report",
        "when": "detected",
        "state": "any",
        "action": "send",
        "receiverId": "control",
        "once": true
      }
    ]
  }
}
```

この2オブジェクトを`units[]`または`groups[].template`へ設定する。

| フィールド | 意味・範囲 |
|---|---|
| `communication.enabled` | 送信能力を有効にするboolean |
| `communication.range` | 最大通信距離、0より大きく100000m以下 |
| `communication.delay` | 成功した情報が届くまでの固定遅延、0～86400秒 |
| `communication.probability` | 送信試行1回の成功確率、0～1 |
| `communication.terrainLOS` | 送信時の両者の位置間で直線の地形遮蔽を判定 |
| `behavior.hold` | trueなら指令が来るまで経路の開始位置で待機 |
| `behavior.preparation` | 指令後の固定準備時間、0～86400秒 |
| `behavior.rules` | 最大16件の条件付き行動 |
| `rules[].id` | 同一Entity内で重複しない英数字・_・-、1～50文字 |
| `rules[].when` | `detected` / `received` / `arrived` |
| `rules[].state` | `any` / `waiting`。waitingは指令待ち・待機・出発待ち。準備中・移動中・到着・地形停止を含まない |
| `rules[].action` | `send` / `depart` |
| `rules[].receiverId` | send時に必要。存在する単体ユニットのID |
| `rules[].once` | trueは条件に合う最初のイベントで一度、falseは新しいイベントごと |

### 探知

成功条件がある場合は`mission.observerFaction`のセンサーが`mission.targetFaction`（任意の`targetIds`で絞る）の対象を探知する。成功条件を設定せずに行動だけを再生する場合は、センサーが自陣営以外の非中立ユニットを探知する。探知確率・対象領域・地形遮蔽は既存の距離モデルを使う。

行動ありでは各観測側と対象の組合せごとに初回探知イベントを発生させる。あるUUVの報告が失敗しても、他のUUVによる独立した初回探知から報告できる。成功条件の探知数は対象IDで重複を除く。「繰り返し」は新しいイベントに反応する意味で、センサーの再探知・継続追尾・定期送信ではない。

### 通信

送信側の能力を使う。送信時の3D距離がrange以下、受信側の初期配置が有効、必要なら地形の直線遮蔽なし、確率抽選に成功した場合に、delay後の受信イベントを予定する。受信側にcommunicationの設定は不要。移動中のリンク維持・受信時の距離再判定・帯域・伝搬物理・媒体や陣営による接続制限・自動再送は未実装。

探知情報には対象ID、観測時刻、観測位置を含め、その後の中継でも同じ観測値を保持する。受信時の対象の現在位置へ自動更新しない。到着から送信する場合、対象情報がない通知も送れる。受信ルールは送信者やメッセージ種別で絞る機能をまだ持たない。

once=trueの送信ルールは、送信失敗も一度の実行に数える。中継ルールをonce=falseにすると、別のUUVからの報告にも反応できる。同じ情報が同じ個体・ルールを循環して再実行されることは防ぐ。中継の因果連鎖は64段、イベントと待ち行列は5万件まで。上限超過は結果として成功／失敗を出さず、計算エラーにする。

### 待機と出発・到着

出発ルールはhold=trueに設定する。最初に実行できた出発ルールを採用し、その受信などのイベント時刻 + preparation + 既存motion.startDelayから抽出した遅れ、を出発時刻とする。各個体は一度しか出発しない。時刻を巻き戻すと指令待ち・準備・移動の状態も再現される。

出発後は既存の初期配置・周回位相・経由点・速度・生成済み航跡を使う。経路の切り替え・迎撃経路生成・移動中の再指令はまだない。ルールがなくhold=trueなら待機を継続する。

到着イベントは、地形制約のない一度だけの経路で、経路長>0、実際の速度>0の場合に生成する。経由点なし・速度0・周回・往復・無効な初期配置・途中で制約により停止する経路では到着成功にしない。空中ユニットの待機は位置固定の抽象表現であり、地上からの離陸・上昇を意味しない。

## 到着を評価するミッション

```json
{
  "type": "arrive",
  "observerFaction": "friendly",
  "targetFaction": "hostile",
  "join": "any",
  "deadline": 2100,
  "responderIds": ["response-uav"]
}
```

`type: detect`の従来条件も使える。arriveの`responderIds`には到着を評価する単体IDを1つ以上指定する。anyは一つ以上、allは全指定ユニットが期限内に到着した場合に成立する。期限ちょうどの到着を含む。自動移動ユニットの到着も評価でき、探知・通信は成功条件に暗黙で強制しない。探知後の対応を評価する場合は、対応ユニットをhold=trueにし、受信→出発ルールを設定する。

再生は終了時刻まで計算し、期限後の探知・到着も履歴に残す。期限後に到着しても成功条件を後から成立させない。モンテカルロは期限まで計算する。両者は期限まで同じイベント・成否を生成する。

## 共通パラメータと結果保存

| 意味上のキー | Entity内の正本 | 表示単位 |
|---|---|---|
| `extent.communication.radius` | `communication.range` | km |
| `interaction.communication.delay` | `communication.delay` | s |
| `interaction.communication.probability` | `communication.probability` | % |
| `behavior.preparation` | `behavior.preparation` | s |

通信が有効な対象では通信変数、behaviorがある対象では準備時間を比較・一様分布・三角分布の抽出に使える。準備時間は行動の設定であり、Rateではない。群のひな型の抽出値は全個体で共通。個体差は既存のmotionを利用する。

条件付き行動ありの結果は`SimSim-analysis` version 3、モデル`event-actions-v1`。各試行に従来の値に加え`reachedCount`と`responderCount`を保存する。通信・ルール・対応ユニット・抽出値はsourceに含まれ、再現時にイベントを再計算する。保存結果の読み込みは構造・対象・成否・件数・時刻・抽出値を検証し集計を作り直すが、保存済み成否自体の再シミュレーション検証は行わない。

行動なしは従来のversion 2・range-hazard-v1のまま。旧version 1／2結果も読み込める。旧結果へ行動を追加して計算モデルが変わった場合は、以前の成否を新モデルの結果として読み込まない。

## 時間分解能と乱数

探知は固定間隔の中点位置で判定し末尾に記録する。中点以前の予定済み通信・出発・到着を先に処理してから位置を評価し、区間末尾までのイベントを時刻順に処理する。通信遅延や到着時刻は区間境界へ丸めないが、探知には判定間隔の近似が残る。区間中の厳密な運動積分ではないため、判定間隔を変えた比較も必要。

通信の乱数はシード・試行番号・送信側ID・初回探知の観測側と対象・経由するルールと送信先に依存する。探知時刻やイベント処理の通し番号に依存させず、個数・探知距離の比較で同じ情報の通信抽選を共有する。通信イベントの追加は、他の観測側の探知抽選の時間格子を変更しない。描画・時刻移動は乱数を消費しない。
